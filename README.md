# 오너뷰 (OwnerView)

**중소기업 대표를 위한 경영 OS.** 통장·카드·세금계산서·전표·재고·프로젝트·근태·급여·결재·메신저·전자계약까지, 흩어져 있던 회사 운영을 한 화면에 모아 자동으로 이어 줍니다.

- 서비스: https://www.owner-view.com
- 무료 요금제로 카드 등록 없이 시작할 수 있고, 기능은 전부 열려 있으며 발행·서명 같은 횟수만 제한됩니다.

## 무엇을 하는 제품인가

소규모 회사는 은행 앱·홈택스·엑셀·메신저·캘린더를 따로 쓰면서 같은 숫자를 여러 번 옮겨 적습니다. 오너뷰는 그 원천 자료를 **자동으로 가져와** 서로 이어 줍니다.

- 통장·카드 거래가 매일 자동 수집되고, 세금계산서·현금영수증은 국세청에서 받아옵니다.
- 수집된 증빙이 **전표**가 되고, 전표가 **손익·부가세 신고·월결산**이 됩니다.
- 상품 하나가 팔리면 **재고·원가·이익**이 같이 움직입니다.
- 출퇴근 한 번이 **근태 현황·연차·급여명세서**로 이어집니다.
- 견적서가 계약서·전자서명·세금계산서·매출 스케줄로 이어집니다.
- 매일 아침 **AI 브리핑**이 오늘 챙길 것을 정리하고, **AI 참모**가 회사 상태를 묻는 말에 답합니다.

한 회사 안에서 역할은 **마스터**와 **멤버** 둘뿐이고, 멤버는 마스터가 준 **권한(메뉴·탭 단위)**만큼만 봅니다.

## 기능 지도

메뉴 구성 그대로입니다. 각 메뉴는 권한 카탈로그(`src/lib/permissions.ts`)의 키와 1:1로 대응합니다.

|---|---|
| 대시보드 | 신호 6칸(미수·매출·통장·카드·프로젝트·근태)과 오늘 챙길 것. 위젯을 끌어 배치 |
| 알림 | 결재·휴가·서명·수집 결과 등 회사 안에서 생기는 모든 알림 |

## 데이터가 흐르는 방식

```
은행·카드사 ──CODEF──▶ bank_transactions / card_transactions ──▶ 수집·전표 ──▶ journal_entries
국세청 ─────CODEF──▶ tax_invoices / cash_receipts ──────────────┘          │
                                                                          ▼
품목·주문·판매·생산 ──▶ stock_moves ──▶ 원가·이익                    손익 · 부가세 · 월결산 · 자금 전망
출퇴근 ──▶ attendance_records ──▶ 연차·수당 ──▶ 급여명세서
견적 ──▶ 계약 ──▶ 전자서명 ──▶ 세금계산서 + 매출 스케줄
```

- 모든 표는 `company_id`로 회사 단위 격리되고, **RLS(행 수준 보안)**가 마스터·권한을 서버에서 강제합니다. 화면의 권한 검사는 UX일 뿐 최종 판정은 DB가 합니다.
- 파생 숫자(연차 사용일수, 저장공간 사용량 등)는 **DB 트리거가 원천에서 다시 계산**하고, 새벽 크론이 대조·보정합니다.
- 회계 마감으로 잠근 달은 전표 입력·정산 확정이 서버에서 막힙니다.
- 수집·발행 같은 자동화는 실패를 숨기지 않고 `sync_logs`·`error_logs`에 남기며, 운영자 화면에서 회사별로 봅니다.

| 영역 | 상대 | 쓰임 |

| 국세청 | CODEF(팝빌 경유) | 전자세금계산서·전자계산서·현금영수증 발행과 수정발행, 사업자번호 검증 |
| 결제 | Stripe · Toss Payments | 구독 결제, 좌석·저장공간 팩, 웹훅 |
| 메일 | Resend | 결재·계약·급여명세·초대·발행 알림 |
| 알림톡 | NHN Cloud | 카카오 알림톡(템플릿 심사 후 사용) |
| 푸시 | Web Push(VAPID) | 브라우저 알림 |

## 기술 구성

- **프론트/서버**: Next.js 16 (App Router) · React 19 · TypeScript 5.9 · Tailwind CSS 4 · TanStack Query 5
- **데이터**: Supabase (Postgres · RLS · Storage · Auth) · 마이그레이션 681개 · 엣지 함수 50개(Deno)
- **문서 처리**: jsPDF · pdf-lib(양식 오버레이) · SheetJS(엑셀)
- **테스트**: Vitest(단위 · 49파일) · Playwright(E2E·화면 점검)
- **배포**: Vercel(웹) · Supabase(DB·엣지) · GitHub Actions(preflight)

엣지 함수는 역할별로 나뉩니다. 수집(`codef-sync`, `hometax-sync`, `cashbill-purchase-sync`), 발행(`hometax-issue`, `modify-tax-invoice`, `cashbill-issue`, `process-invoice-queue`), 서명(`complete-signing`), 결제(`stripe-webhook`, `toss-*`), 알림(`send-*`, `send-web-push`, `send-kakao-alimtalk`), AI(`ai-briefing`, `owner-copilot`, `settlement-ai-match`, `parse-*`), 운영(`daily-report`, `operator-user-admin`). 공용 모듈(`_shared/`)에 타임아웃 fetch, 메일 가드, Sentry 래퍼, 데이터 점검이 있습니다.

## 개발 환경 준비

```bash
npm install
cp .env.example .env.local   # 값을 채운다
npm run dev                   # http://localhost:3000
```

필요한 환경변수는 `.env.example`에 이름만 있습니다. Supabase URL·키, Toss 클라이언트/시크릿, CODEF 클라이언트, 홈택스 API 키입니다. 엣지 함수의 비밀값(Resend·Anthropic·VAPID·NHN 등)은 Supabase 프로젝트 시크릿으로 둡니다.

마이그레이션은 Supabase 대시보드가 아니라 원장 스크립트로 적용합니다. 이렇게 해야 CI의 DB 게이트가 적용 여부를 확인할 수 있습니다.

```bash
node scripts/apply-supabase-migration.mjs supabase/migrations/<파일>.sql
node scripts/apply-supabase-migration.mjs --query "select 1"   # 읽기 확인
```

## 검사와 배포

푸시 전에 도는 것들입니다.

| 명령 | 확인하는 것 |
|---|---|
| `npm run typecheck` | 타입 오류 0 |
| `npm test` | 단위 테스트 (Vitest) |
| `npm run check:unpaged` | 회사 전체 조회에 페이징이 빠져 1,000행에서 잘리는 곳이 늘지 않았는지 |
| `npm run check:date-inputs` | 기본 날짜 입력 대신 공용 DateField를 쓰는지 |
| `npm run preflight` | 마이그레이션 원장 · RLS 스모크 · DB 가드 · 요금제 자격 스모크 |
| `npm run qa:seed` / `qa:teardown` | 시연·검증용 가상 회사 만들기·지우기 |

- `main`에 푸시하면 Vercel이 자동으로 운영 배포합니다. 엣지 함수는 `supabase functions deploy <이름>`으로 따로 배포하고, 배포 전 `esbuild`로 구문을 확인합니다(타입검사 범위 밖).
- GitHub Actions `preflight`가 타입검사·테스트·빌드·DB 게이트를 돌립니다.
- 두 대의 PC가 `main`에 직접 푸시하므로, 작업 시작 전 `git fetch && git rebase origin/main`, 전역 파일과 DB 변경 전에는 상대 PC에 알리고, `git add -A`는 쓰지 않습니다. 자세한 규칙은 `CLAUDE.md`에 있습니다.

## 설계 원칙

- **원인을 고친다.** 화면 단위 땜질 대신 규칙을 한 모듈로 모아 같은 원인이 닿는 화면을 함께 고칩니다. 예: 견적 합계(`quote-total`), 통장 갈래(`bank-accounts`), 재고 부호(`editQtyOf`), 격자 키보드(`use-grid-keys`).
- **거짓 UI를 두지 않는다.** 동작하지 않는 기능을 버튼·토글·안내문으로 보이게 하지 않습니다. 저장만 되고 아무 효과가 없는 설정은 만들지 않습니다.
- **실패를 숨기지 않는다.** 조회 실패를 0건으로, 저장 실패를 성공 토스트로 보이게 하지 않습니다. 실패는 기록하고 사용자에게 말합니다.
- **사용자 데이터를 추측으로 고치지 않는다.** 되돌리려면 원본 근거가 있어야 하고, UPDATE·DELETE는 범위를 좁혀 영향 행을 셉니다.
- **기획 순서.** 화면보다 "무엇을 기준으로 판단하는가"를 먼저 정하고, 결정마다 규칙·AS-IS/TO-BE·적용 시점·기존 데이터 처리를 적습니다(`docs/PLANNING_METHOD.md`).
- **조회 화면 표준과 디자인 시스템**은 `CLAUDE.md`와 `docs/DESIGN_SYSTEM.md`가 원본입니다.
