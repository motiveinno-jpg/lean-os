## ① History — 지금 메뉴가 왜 이 모양인가

- 공개 페이지(`/demo` · `/features` · 랜딩 메가메뉴)가 보여 주는 메뉴는 **단일 출처**에서 온다:
  `src/components/landing-v8/catalog.ts` 의 `CATALOG` (9그룹 51메뉴).
- 랜딩 문구는 이미 「되는 것만 적는다」로 관리돼 왔다. 코드 주석이 증거다:
  - `2026-09-14 「분석 › KPI 현황판」은 없는 자리였다` → 지운 흔적
  - `08-25 「계약 갱신 알림」은 미동작이라 뺐다`
  - `「회사 API 키로 주문을 직접 받아」 → 실제 회사 키로 검증 전이라 되는 것만 적는다`
- 즉 **과장 광고를 지우는 방향으로는 이미 여러 번 손이 갔다.**

## ③ 자문자답 — 무엇을 기준으로 "신설해야 한다"고 판단하나

**Q1. 무엇을 기준으로 메뉴를 새로 만드나?**
「기능이 없다」가 아니라 **「업무가 끊긴다」** 를 기준으로 한다.
화면이 이미 있는데 못 찾는 것은 *신설*이 아니라 *노출* 문제다. 메뉴를 늘리면 못 찾는 메뉴가 하나 더 늘 뿐이다.

**Q2. 사용자는 이걸 왜 하는가?**
오너뷰를 쓰는 이유는 "도구를 줄이려고"다. 새 메뉴가 **다른 도구 하나를 없애지 못하면** 만들 이유가 약하다.

**Q3. 반대 경우는?**
메뉴를 만들면 **빈 화면**이 되는 경우. 오늘 실측에서 이 함정이 두 번 나왔다:
- `documents.contract_end_date` 칸은 있는데 **입력된 값 0건**(문서 62건 중)
- `partners.payment_terms_days`(오늘 신설) 도 아직 전 거래처 미입력
**입력받는 자리를 먼저 만들지 않으면 대장을 만들어도 빈 표다.**

**Q4. 자동으로 못 푸는 것은?**
계약 기간·결제조건·급여일 같은 값은 **회사가 알려 줘야만** 알 수 있다. 수집으로 못 채운다.
그래서 이런 기능은 「입력 자리 → 쌓임 → 보는 화면」 순서를 지켜야 하고, 순서를 뒤집으면 반드시 빈 화면이 된다.

## ④ 결정

### 결정 1 — 급여를 인사 그룹의 메뉴로 올린다 (1순위, 신설 아님·노출)

| | |
|---|---|
| **규칙** | 랜딩·요금제·소개 메일이 앞세우는 기능은 사이드바에서 한 번에 보여야 한다. |
| **AS-IS** | 급여는 `/employees` 안의 탭이다. 사이드바 인사 그룹은 구성원·근태 관리·근로계약·서식 **3개뿐**. |
| **TO-BE** | 인사 그룹에 「급여」 추가 → `/employees?tab=salary`. 화면은 그대로 쓴다. |
| **적용 시점** | 즉시. 화면을 새로 만들지 않으므로 위험이 거의 없다. |
| **기존 데이터** | 영향 없음. |

**왜 1순위인가.** 소개 메일에 「출근 기록이 그대로 급여와 명세서가 됩니다」를 적어 놓고,
가입한 사람이 사이드바에서 급여를 못 찾는다. 광고와 첫 화면이 어긋나는 자리다.
비용은 `sidebar.tsx` 한 줄 + 권한 카탈로그 확인이다.

⚠️ 메뉴를 늘리면 `lib/permissions.ts`(PERMISSION_CATALOG)·`lib/route-labels.ts` 동기화가 필요하다(CLAUDE.md).
급여는 이미 `/employees:salary` 권한 키가 있으므로 **새 키를 만들지 않고 그 키를 쓴다.**

### 결정 2 — 계약 대장은 「입력 먼저, 대장 나중」 2단계로 간다

| | |
|---|---|
| **규칙** | 보는 화면보다 **값이 들어오는 자리**를 먼저 만든다. |
| **AS-IS** | `documents.contract_start_date / contract_end_date / contract_amount` 칸은 **이미 있다.** 그런데 문서 62건 중 **입력된 값 0건**. 계약 갱신 리마인더 엣지는 2026-07-29 봉인(한 번도 동작 안 함). 만료가 다가와도 아무도 모른다. |
| **TO-BE** | **1단계**: 계약서를 저장할 때 계약 기간을 실제 칸에 쓰게 한다. 지금 `BoardDocModal` 은 계약기간을 화면에서 받지만 `content_json` 에만 넣는다 — 같은 값을 컬럼에도 쓴다(조회 가능해진다).<br>**2단계**: 값이 쌓인 뒤 「업무 › 계약」 대장 신설 — 만료 임박·자동 갱신·종료 목록 + 대시보드 신호 + 알림(`contract_expiry` 타입은 이미 제약에 있다). |
| **적용 시점** | 1단계 먼저. 2단계는 계약 기간이 채워진 계약이 **10건 이상** 쌓인 뒤. |
| **기존 데이터** | 옛 계약 62건은 기간이 비어 있다. 소급 입력은 강제하지 않는다 — 대장에서 "기간 미입력" 으로 모아 보여 주고 거기서 채우게 한다. |

**왜 2단계인가.** 1단계 없이 대장을 만들면 62건 전부 "기간 없음"으로 뜨는 빈 표가 된다.
오늘 자금 전망에서 겪은 것과 같은 구조다(칸을 만들었지만 아직 값이 없다).

### 결정 3 — 신설하지 않기로 한 것과 그 이유 (재제안 금지)

| 후보 | 판정 | 이유 |
|---|---|---|
| **영업 · CRM** | 신설 안 함 | 랜딩 비교표가 'CRM' 대체를 말하지만, 그 일은 **프로젝트(수익형)** 가 이미 한다(견적→계약→청구 파이프라인). 메뉴를 더하면 딜이 두 곳에 산다. 필요한 것은 새 메뉴가 아니라 **수익형 프로젝트의 이름·진입로**가 영업으로 읽히게 하는 것. |
| **예산 관리** | 보류 | `account_budgets` 표만 있고 코드·화면 0. 5~20명 회사가 계정과목별 예산을 세우는 일이 드물다. 요구한 고객도 없다. **수요 근거가 생기면 다시 본다.** |
| **고객 문의함(고객사의 CS)** | 보류 | 데이터 0, 요청 0. 업종 페이지에도 없다. 지금 만들 근거가 없다. |
| **견적 추적(quote_tracking)** | 폐기 | 표만 있고 완전 미사용. 열람 추적은 `document_share_views` 가 담당한다. **표를 지울지는 별도 판단**(데이터 0). |
| **연말정산** | 보류 | `year_end_tax_status` 는 구성원 화면이 이미 참조한다. 독립 메뉴로 뺄 만큼 쓰지 않는다. |

## ⑤ 누락 점검 (PLANNING_METHOD ④)

- **권한·RLS** — 결정 1은 기존 `/employees:salary` 키를 쓴다(새 키 없음 → 백필 불필요).
  결정 2의 계약 대장은 새 키가 필요하다 → **새 메뉴는 권한 백필 필수**(member_permissions 행이 없으면 마스터 외 아무도 못 본다).
- **역할** — 급여는 금액이라 `money: true`. 직원 기본 노출 금지(2026-08-26 방침 유지).
- **빈 상태** — 결정 2의 1단계가 이것을 막기 위한 장치다.
- **경계값** — 계약 종료일이 과거인 것(이미 만료)·종료일 없는 무기한 계약 두 가지를 분리해 보여야 한다.
- **중복 실행·마감·되돌리기** — 해당 없음(읽기 화면).
- **모바일 폭** — 대장은 표라 가로 스크롤 한 겹 필요.
- **기존 데이터** — 위 표에 적음.

**「광고했는데 없는 메뉴」는 없다. 진짜 문제는 ① 급여처럼 있는데 안 보이는 것과
