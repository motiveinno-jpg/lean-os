# 조회 표준(query-kit) 확산 계획 — 2026-08-18

> 사장님 지시: "신규 공용 UI 컴포넌트를 가지고 다른 메뉴에 확산한다. 어떤 메뉴에 어떻게 적용할지 기획할 것.
> 다른 메뉴의 기존 UI들 다 바뀌어도 됨. 통일성을 위해 신규 공용 UI 컴포넌트 디자인을 최우선으로 한다."

부품: `src/components/query-kit.tsx`(QueryBar·검색조건 패널·빠른검색·걸린 조건 칩·ResultStrip·Pager·SelectionBar·AI 제안·엑셀·내 조건)
· `sortable-th.tsx`(머리단 정렬 ▼·≡ 필터·열 너비) · `pick-list.tsx`(키보드 검색 선택). 새 툴바는 만들지 않는다.

## 0. 기준 하나 — 화면이 하는 일로 가른다

| 유형 | 화면이 하는 일 | 적용 수준 |
|---|---|---|
| **A 조회·처리** | 목록을 조회해 고르고 처리한다 | 표준 **전면**: 1줄 조회(기간·검색조건·빠른검색·상태칩 ‖ AI 제안·주 실행) → 걸린 조건 칩 → 2줄 결과 → 표(SortableTh, 50줄 Pager) → 3줄 SelectionBar |
| **B 입력 + 조회** | 한 장을 입력하는 화면인데 아래·옆에 목록이 있다 | 입력부는 그대로, **목록부만** 표준(조회줄·표·Pager). 파란 버튼은 '저장' 하나 |
| **C 리포트** | 숫자를 읽는다(조회 대상이 기간뿐) | report-kit 유지. **기간 조회줄만 QueryBar**, 표 머리단만 SortableTh 색·정렬·≡ |
| **D 피드·카드·달력** | 글·카드·일정을 훑는다 | 표준 대상 아님. 상단 검색줄만 QueryBar 모양으로 맞춘다 |

"표가 있느냐"가 기준이 아니다 — 리포트에도 표는 있다. **사용자가 조건을 걸어 줄을 고르는가**가 기준이다.

## 1. History — 지금 왜 이 모양인가
- 2026-08-12~13: 수집·전표(5탭)·세금·증빙·통장·카드·전자계산서에 query-kit + sortable-th 적용(사장님 확정 표준).
- 그 밖 화면은 각자 툴바를 갖고 있다: `partner-filter-pop`(거래처), `projecthub-toolbar`, `board-toolbar`, `approval-filters`,
  `voucher-entry-toolbar`, `partner-reconciliation-toolbar`, `partner-manual-toolbar`, 문서함·전자계약의 자체 검색+페이지… **같은 일을 하는 툴바가 8벌 이상.**
- 여러 화면이 조회 조건을 localStorage 에 기억한다(거래처 필터, 프로젝트 렌즈 등). 표준은 **자동 기억 금지 · 내 조건(DB saved_queries)**.
- 표 머리단은 화면마다 색·정렬표시·필터 유무가 다르다(오늘 세금·증빙에서 확인한 그 문제).

## 2. 자문자답
1. **무엇을 기준으로 판단하는가** — 위 A/B/C/D. 화면 하나에 여러 성격이 섞이면(프로젝트: 목록+칸반+상세) 목록 탭만 A.
2. **사용자는 왜 이걸 하는가** — 메뉴마다 조회법을 다시 배우지 않게. 조건·결과·확정이 어디서나 같은 자리에 있어야 손이 먼저 간다.
3. **반대 경우** — 입력이 주인 화면(일반전표·매입매출전표)에 조회줄을 위에 올리면 입력이 밀린다 → B. 대시보드·경영요약·자금전망은 조건이 없다 → 제외. 달력은 표가 아니다 → D.
4. **자동으로 못 푸는 것** — 조건 목록은 화면마다 다르다(거래처엔 기간이 없다, 근태는 사람×달). 표준은 **줄 나눔과 부품**이지 조건 목록이 아니다. 조건은 아래 표에 화면별로 적는다.
5. **확정할 게 없는 화면**(대출·자산·서식) — SelectionBar 없음. 그래도 파란 버튼은 화면에 하나(주 실행: +등록)만.

## 3. 결정
1. **부품 고정** — query-kit·sortable-th·pick-list 만 쓴다. 화면 고유 툴바 CSS 는 걷어내고 `docs/REMOVED_CODE_LOG.md`에 적는다.
   적용 시점: 화면 전환 커밋과 같은 커밋. 기존 데이터: 없음(순수 UI).
2. **조회값 자동 기억 금지** — localStorage 조회 조건 읽기·쓰기 코드 삭제(열 너비 키만 남긴다). 편의는 내 조건(★ 기본)으로.
   기존 데이터: 옛 localStorage 키는 **읽지 않는다**(지우는 코드는 넣지 않는다 — 있어도 해가 없다).
3. **기간 기본값 최근 1개월**(`defaultRange`). 월 단위 화면(정기 지출·급여·부가세)은 `defaultRangeMonth`. 기간이 없는 마스터 화면(거래처·구성원·서식)은 기간 칸 없이 상태 칩만.
4. **표** — SortableTh(정렬 ▼·≡ 필터·너비 조절), 기본 50줄 Pager, 머리단 가운데·숫자 오른쪽·긴 글 왼쪽, 세로선은 머리단만.
5. **파란 버튼 하나** — SelectionBar 가 있으면 거기, 없으면 주 실행 하나. 나머지는 흰(secondary).
6. **AI 제안 그릇** — 화면의 보조기능(추천·대조·조회)은 여기로 모으고 줄마다 출처(`AI 추천`/`내가 배운 규칙`/`국세청 조회`/`장부 대조`). 그릇 밖에 혼자 설 때만 'AI'를 붙인다.
7. **엑셀** — 화면마다 다른 내보내기 버튼은 `ExcelMenu` 하나로(현재 조회 결과 / 전체).
8. **순서(Wave)** — 도메인 인접·데이터 많은 것부터. Wave 하나 = 커밋 여러 개(화면 단위), 커밋마다 AS_IS ▶ TO_BE·버린 안·prod 캡처.

## 5. 누락 점검 (PLANNING_METHOD ④)
- 권한·RLS: 해당없음(읽기 UI 재편, 데이터 접근 규칙 안 바뀜). **역할**: 직원 화면도 동일 표준(role 분기 없이) — 디자인 통일 원칙.
- 빈 상태: ResultStrip "0건" + 표 안 한 줄 문구("조건에 맞는 줄이 없습니다 — 검색조건을 풀어 보세요") 표준 문구 하나로.
- 경계값: 기간 역전(from>to → 자동 교환), 금액 음수·0, 줄 수 500 상한.
- 중복 실행: SelectionBar 버튼 busy 잠금(이미 부품에 있음).
- 마감: 해당없음. 기존 데이터: localStorage 조회 조건 무시(결정 2). 열 너비 키는 유지.
- 파급 화면: 각 화면의 하위 컴포넌트가 툴바 상태(state)를 props 로 받는 곳 — 화면마다 grep 해 목록으로 커밋에 남긴다.
- 외부 전송: 없음. 인쇄·엑셀: ExcelMenu 통일(결정 7). 모바일 폭: QueryBar 는 줄바꿈, 표는 가로 스크롤(이미 부품 규칙). 되돌리기: 해당없음.

## 6. 파급 — 공용 파일
- `globals.css`: 새 클래스 추가 없이 기존 `qk-*`·`ev-table`·`th-*` 만 쓴다. 화면 고유 툴바 클래스는 삭제(줄어든다).
- `report-kit.tsx`(Wave 5): 표 헤더를 SortableTh 로 바꾸면 리포트 전부에 파급 — 그 커밋에서 리포트 6개 캡처 대조.
- 두 PC 규칙: UI 구조 변경은 이 PC(연준호)에서만. 다른 PC 는 그동안 같은 화면을 만지지 않는다.

## 7. 진행 방식
- Wave 순서대로, 화면 하나 = 커밋 하나. 커밋 메시지: History → 바꾼 것 → 버린 안 → 검증(prod 캡처).
- 각 화면 착수 전 5분 History(왜 그 툴바가 있었나) — 없애도 되는 이유를 적고 없앤다.
- Wave 1 끝날 때마다 사장님 화면 확인 → 다음 Wave.
