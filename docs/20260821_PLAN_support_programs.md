## ① History — 지금 왜 이 기능이 없나

- 오너뷰는 지금까지 **회사 안에서 벌어진 일**(통장·전표·직원·계약)만 다뤘다. 바깥에서 들어오는
  기회(정부 지원사업)는 다룬 적이 없다. 흔적은 세 군데뿐이다.
  - `src/app/(app)/reports/flow/_components/FlowMatrix.tsx:57` — 자금 전망에 **`보조금/지원금` 행이 이미 있다**
    (들어온 뒤의 돈만 본다).
  - `src/app/(app)/loans/page.tsx:172` — 대출 종류에 `정책자금` 이 있다(빌린 뒤만 본다).
  - `src/lib/project-boards.ts:117` — 프로젝트 템플릿 설명에 "정부지원사업 정산" 이 있다(선정된 뒤만 본다).
- 즉 **"받은 다음"은 전부 있는데 "찾는 단계"만 비어 있다.** 이 기획은 그 앞단을 채운다.
- 회사 프로필(`companies`)에는 이미 `industry / business_type / business_category / address /
  business_number / representative` 가 있고, `employees` 에는 `birth_date / hire_date /
  resignation_date / employment_type / is_4_insurance / salary` 가 있다.
  **판정에 필요한 값 대부분을 우리는 이미 갖고 있다.** 이것이 이 기능을 우리가 만들 이유다.

## ② 자문자답

**Q1. 무엇을 "기준"으로 적합하다고 판단하는가?**
화면·버튼이 아니라 이것부터 정한다. 판단 기준은 **회사 프로필 6축 ↔ 공고 자격 스펙**의 대조다.

| 축 | 값 | 출처 |
|---|---|---|
| 1 업종 | 표준산업분류(KSIC) 대분류 + 업태·종목 | `companies.industry/business_type/business_category` (자유 텍스트 → KSIC 추정 후 **사람 확인**) |
| 2 소재지 | 시도 · 시군구 | `companies.address` 파싱 |
| 3 규모 | 상시근로자 수 · 최근 12개월 매출 | `employees`(재직) · 기존 손익 집계 재사용 |
| 4 업력 | 개업일 기준 창업 3년/7년 이내 | **우리에게 없음 → 회사 카드 입력** |
| 5 고용 | 만 34세 이하 인원, 최근 3개월 신규 채용, 최근 3개월 감원 유무, 4대보험 가입, 월보수 구간 | `employees.birth_date/hire_date/resignation_date/is_4_insurance/salary` |
| 6 자격·인증 | 벤처·이노비즈·여성기업·장애인기업·수출실적·기업부설연구소·기존 수혜 이력 | **우리에게 없음 → 회사 카드 입력** |

**Q2. 사용자는 이걸 왜 하는가?**
대표는 "지원금이 있다"는 건 알지만 **어디에 뭐가 열렸는지 찾을 시간이 없다.** 그래서 컨설팅 업체에
성공보수를 준다. 우리가 노리는 건 목록 제공이 아니라 **"우리 회사 기준으로 이미 걸러진 것"** 이다.
기업마당에 가면 목록은 누구나 본다 — 우리의 값은 **회사 데이터로 걸러 준다**는 것 하나다.

**Q3. 반대 경우(예외)는?**
- ㉠ **맞는 게 하나도 없는 회사** — 신설·1인 기업·특수 업종. → 빈 화면 대신 "무엇을 채우면 몇 건이
  더 보이는지"를 보여준다(회사 카드 완성도 %).
- ㉡ **너무 많이 맞는 회사** — 전 업종 공통 공고가 수십 건. → 기본 정렬은 건수가 아니라
  **마감 임박 + 예상 수령액**. 상위 5건만 '추천'으로 세우고 나머지는 목록으로 내린다.
- ㉢ **작년에 이미 받은 회사** — 중복 수혜 제한이 있는 사업이 있다. → 수혜 이력을 회사 카드에 담고
  "작년 수혜 — 재신청 제한 확인 필요"로 경고.

**Q4. 자동으로 못 푸는 것은?**
- **최종 자격 판정은 우리가 못 한다.** 공고문의 예외 조항·주관기관 재량은 텍스트만으로 결정되지 않는다.
  → 판정을 2단(맞다/아니다)이 아니라 **3단**으로 둔다: `가능성 높음 / 조건 확인 필요 / 해당 없음`.
  **애매하면 '조건 확인 필요'** 로 보낸다(놓치는 것보다 낫다).
- **개업일·인증·수출실적**은 우리 DB에 없다. 홈택스 연동은 BLOCKED 영역이라 못 가져온다.
  → **사람이 한 번 채운다**(회사 카드). 안 채워도 동작하되, 채우면 정확도가 올라간다고 화면에 적는다.
- **신청 대행은 하지 않는다.** 우리는 찾아 주고 챙겨 줄 뿐이고, 신청은 각 기관 사이트에서 한다.

## ③ 결정

### 결정 1. 공고 해석은 **회사별로 하지 않는다** — 공용 1회 + 회사별 대조

- **규칙** — 공고 원문의 AI 해석(자격 스펙 추출)은 **플랫폼 전체에서 공고 1건당 딱 1회**만 한다.
  회사별 적합 판정은 그 결과(구조화 JSON)와 회사 프로필을 **코드/SQL 로 대조**한다.
  AI 를 두 번째로 쓰는 곳은 **상위 N건의 '왜 맞는지' 설명 생성**뿐이다.
- **AS_IS ▶ TO_BE** — (없음) ▶ 공용 `gov_programs` + 회사별 `gov_program_matches`.
- **적용 시점** — Phase 2(스펙 추출)부터. Phase 1은 규칙 필터만으로도 동작한다.
- **기존 데이터** — 해당 없음(신규).
- **버린 안**: 회사마다 LLM 이 공고 전문을 읽게 하는 안.
  회사 1,000곳 × 활성 공고 3,000건이면 매일 300만 회 호출 — 비용이 매출을 넘고, 같은 공고에 대해
  회사마다 다른 해석이 나와 근거를 신뢰할 수 없다.

### 결정 2. 수집원은 **3계통**으로 나눈다 (성격이 달라 한 통에 못 담는다)

| 계통 | 무엇 | 방식 | 비고 |
|---|---|---|---|
| A **공고형** | 중앙부처·지자체·유관기관 지원사업 공고 | 기업마당 API `https://www.bizinfo.go.kr/uss/rss/bizinfoApi.do` (`crtfcKey`·`searchLclasId` 분야코드·`hashtags` 지역·`pageIndex`) | 지자체까지 이미 통합돼 있다 |
| B **창업형** | 창업 특화 공고 | 공공데이터포털 `창업진흥원 K-Startup 조회서비스`(15125364) | 업력 7년 이내 회사에만 의미 |
| C **상시 제도형** | 고용장려금·두루누리·세액공제 등 **공고가 아니라 항상 열려 있는 제도** | **API 없음 → 수기 카탈로그 20~30건**(연 2회 갱신) | ★ 적중률이 가장 높은 계통 |

- **왜 C 가 핵심인가** — 여기가 오너뷰의 차별점이다. 남들은 공고 제목을 보여주지만, 우리는 직원
  데이터를 갖고 있어 **금액까지 계산**할 수 있다.
  - 예: 재직 8명 중 만 34세 이하 신규 입사 2명, 최근 3개월 감원 없음, 4대보험 가입
    → *청년일자리도약장려금 — 2명 × 연 최대 720만원 = 연 1,440만원 예상*
  - 예: 상시 9명(10인 미만), 월평균보수 270만원 미만 신규 가입자 3명
    → *두루누리 — 국민연금·고용보험 80% 지원, 1인 월 최대 약 24만원 예상*
  - 이 값들은 **이미 우리 화면에 있는 숫자**다. 사장님이 아무것도 입력하지 않아도 나온다.
- **버린 안**: 지자체 홈페이지 직접 크롤링. 유지보수 지옥 + 사이트별 이용약관 위험. 기업마당이 이미 통합한다.

### 결정 3. 판정은 **3단 + 근거 문장**. 점수(%)는 쓰지 않는다

- **규칙** — 각 건은 `가능성 높음 / 조건 확인 필요 / 해당 없음` 중 하나이고, **반드시 근거 줄을 함께 적는다.**
  - 맞는 근거: "소재지 서울 ✓ · 제조업 ✓ · 상시 8명(5인 이상) ✓"
  - 걸리는 조건: "창업 7년 이내 — **개업일 미입력**, 확인 필요"
- **AS_IS ▶ TO_BE** — (없음) ▶ 조건별 ✓/✕/? 체크리스트가 상세 팝업에 그대로 뜬다.
- **적용 시점** — Phase 1(규칙 필터)에서 이미 ✓/✕/? 가 나온다. Phase 2 에서 문장이 붙는다.
- **버린 안**: 적합도 87% 같은 점수. 근거 없는 숫자는 대표가 못 믿고, 틀렸을 때 어디가 틀렸는지 못 짚는다.

### 결정 4. **모르는 값은 사람이 채운다** — '회사 카드' 7문항

- **규칙** — 우리 DB로 알 수 없는 축(업력·인증·수출·수혜이력)만 묻는다. **7문항, 한 번 입력, 3분.**
  ① 개업일 ② 기업 규모 구분(소상공인/소기업/중기업) ③ 보유 인증(벤처·이노비즈·메인비즈·기업부설연구소·
  여성기업·장애인기업·사회적기업, 복수) ④ 수출 실적 유무 ⑤ 주력 업종 확인(KSIC 추정값을 보여주고 고르게 함)
  ⑥ 최근 3년 정부지원사업 수혜 이력 ⑦ 관심 분야(자금·인력·기술·수출·판로, 복수)
- **AS_IS ▶ TO_BE** — 회사 정보는 `settings` 에 흩어져 있다 ▶ 지원사업 화면 상단에 **완성도 막대**
  (`프로필 5/7 — 2개 더 채우면 매칭 정확도가 올라갑니다`)와 채우기 버튼.
- **적용 시점** — Phase 1. 안 채워도 화면은 돈다(그 조건은 전부 `?` 로 표시).
- **기존 데이터** — 기존 회사는 전부 미입력 상태로 시작. 강제 팝업 금지(작업을 막지 않는다).
- **누가 정하는 값인지** — 전부 **회사 설정값**(대표·관리자만 수정).

### 결정 5. 자리는 **홈 그룹**, 라벨은 `지원사업`, 라우트는 `/support-programs`

- **규칙** — 사이드바 `홈` 그룹, 순서는 `대시보드 · 알림 · 마이페이지 · AI 참모 · **지원사업** · 마스터`.
  홈 그룹 순서 원칙이 "매일 여는 순"이므로, 주 1회 여는 성격인 지원사업은 AI 참모 아래에 둔다.
  권한은 `roles: ["owner","admin"]` (직원 개인정보·급여로 판정하므로 직원에게는 보이지 않는다).
- **동반 수정 필수(CLAUDE.md 규칙)** — `sidebar.tsx` NAV_GROUPS + `NAV_ITEM_COLOR`(홈=블루 계열)
  + `lib/permissions.ts` PERMISSION_CATALOG 홈 그룹 + `lib/route-labels.ts` 세 곳을 한 커밋에서 같이 바꾼다.
- **대시보드 위젯 1개** — `지원사업 — 이번 주 마감 N건 / 예상 수령 가능 N원`(카탈로그 추가, 기본 미노출).
- **버린 안**: `분석` 그룹에 넣는 안. 분석은 *우리 숫자를 보는 곳*이고 이건 *바깥 기회를 찾는 곳*이라 성격이 다르다.
  AI 참모 안의 한 탭으로 넣는 안도 버렸다 — 목록·마감·담기가 필요한 **조회 화면**이라 대화창에 안 맞는다.

### 결정 6. 화면은 **조회 화면 표준** 그대로 (`query-kit`)


- **'AI' 표기 규칙** — 그릇에 AI 가 붙으면 안에서는 뺀다. 상세 팝업의 설명 줄 출처는 `AI 해석`,
  규칙으로 판정한 줄은 `회사 자료 대조`로 각각 적는다(전부 AI 로 뭉뚱그리지 않는다).

### 결정 7. **찾고 끝나지 않는다** — 오너뷰 안에서 이어진다

- 담기 → `일정 / 할 일`에 마감일 등록 · 담당자 지정
- 준비 시작 → **프로젝트 승격**(`예산 · 지출` 템플릿, `lib/project-boards.ts:117` 이 이미 "정부지원사업 정산"을 상정)
- 선정 → 입금 → **자금 전망의 `보조금/지원금` 행**(`FlowMatrix.tsx:57`)과 연결 → 정산까지 한 곳에서.
- **이 연결이 경쟁 서비스가 못 하는 부분이다.** 찾아 주기만 하는 서비스는 이미 많다.

### 결정 8. 갱신과 알림

- **규칙** — `pg_cron` 새벽 1회: ㉠ 신규 공고 수집 ㉡ **신규 건만** 스펙 추출 ㉢ 회사별 매칭 재계산
  ㉣ 마감 지난 건 `closed` 처리. 알림은 **주 1회 요약 1건**(월요일) + `D-3 마감 임박`은 담아둔 건에 한해 즉시.
- **적용 시점** — Phase 3. 그전에는 화면을 열 때 계산한다.
- **버린 안**: 새 공고마다 알림. 하루 수십 건이 뜨면 그날로 알림을 꺼 버린다.

## ⑧ 2차 — 적합도 · 신청 서류 (2026-08-21 사장님 지시)

> "가장 적합하거나 바로 신청할 수 있는 것들의 우선순위가 상단으로, 적합도를 평가해주는 것.
>  그리고 사업신청시 필요한 서류가 어떤 것인지, 회사에 등록된 서류가 있다면 자동으로 끌고오게"

### 결정 9. 적합도는 **세 갈래로 나눈 100점** — 점수만 두지 않는다

- **규칙** — `자격 50 + 서류 30 + 신청 20`. 목록 기본 정렬이 이 점수(내림차순)다.
  - 자격: ✕ 가 하나라도 있으면 **전체 0점**(해당 없음). 전부 ✓ 면 50점. `?` 가 섞이면 아는 것의 비율,
    **바닥은 15점** — 전부 모른다고 0점이면 목록에서 사라져 사람이 판단할 기회가 없어진다.
  - 서류: 준비된 서류 / 필요 서류 × 30. 목록을 모르면 15점(중간).
  - 신청: 접수 중 +10(상시도 +10, 접수 전 +4) · 온라인 접수 +5 · 마감 여유 14일↑ +5 / 7~13일 +3 / 6일↓ +1.
- **AS_IS ▶ TO_BE** — 판정 3단만 있었다 ▶ 판정 배지 **옆에** 점수와 막대. 칸은 늘리지 않았다(판정 칸을 적합도 칸으로 합침).
- **버린 안** — 결정 3에서 "적합도 87% 같은 점수는 쓰지 않는다"고 했었다. 지금도 **맨 숫자는 쓰지 않는다** —
  상세를 열면 `자격 38/50 · 서류 8/30 · 신청 10/20` 과 각 줄의 근거가 그대로 나온다. 점수는 순위를 정할 뿐이고,
  판단 근거는 여전히 문장이다.
- **'지금 신청 가능' 배지** — 접수 중 + 자격에 ✕ 없음 + 필요 서류 전부 준비. 결과 줄의 숫자를 누르면 그 조건으로 좁혀진다.

### 결정 10. 서류는 **사전은 코드, 목록은 DB, 보유 판정은 파일명**

- **규칙**
  - 사전(17종: 사업자등록증·중소기업확인서·완납증명·4대보험 가입자명부·근로계약서·급여대장 …)은 `lib/support-docs.ts`.
    이름·발급처·발급 URL·유효기간은 회사마다 다르지 않다. DB 에 넣으면 링크 하나 고치는 데 마이그레이션이 필요해진다.
  - 사업별 목록만 `gov_programs.required_docs`. 비어 있으면 rule_key 기본 세트(공고형은 공고문을 읽기 전까지 모른다).
  - 보유 판정은 **파일명·폴더명·태그**로 한다 — `document_files.category` 는 프로덕션 51건이 **전부 비어 있다**(실측).
    쓰지 않는 칸을 믿고 짜면 아무것도 안 잡힌다.
- **상태 5가지** — `비슷한 파일` / `다시 발급 필요`(유효기간 초과) / `오너뷰에서`(구성원·근태·회계 자료로 이동)
  / `발급 필요`(홈택스·위택스·고용24 링크) / `직접 작성`.
- **⚠️ '있음'이라고 단정하지 않는다** — 파일명으로 찾은 것이라 그 서류라는 보장이 없다.
  실제로 프로덕션 확인 중 `근로계약서(수습양식_연봉변화없음)-p5.png`(PDF 를 페이지로 쪼갠 **양식 이미지 조각**)가
  "근로계약서 있음"으로 잡혔다. → ①`-p숫자.png` 조각은 후보에서 제외 ②라벨을 '비슷한 파일'로
  ③"✓ 는 파일 이름으로 찾은 것 — 눌러서 확인하세요" 안내를 목록 위에 고정.
  **잘못된 안심을 주느니 한 건 덜 찾는 편이 낫다.**
- **기존 데이터** — 상시 제도 10건의 서류는 시드로 채웠다. 수집형 공고는 기본 세트를 쓴다.
